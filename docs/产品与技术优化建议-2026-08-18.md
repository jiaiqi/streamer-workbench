# 主播工作台产品与技术优化建议

> 文档类型：产品、架构与 UI/UX 综合评估
>
> 评估日期：2026-08-18
>
> 文档状态：评估建议，**不是当前执行主规格**
>
> 适用范围：产品定位、核心任务流、数据与应用架构、桌面壳、渲染运行时、UI/UX、质量门
>
> 真相约束：执行顺序仍以 `AGENTS.md`、主规格、路线图和 ADR 为准；本文只用于帮助确定下一阶段优先级。

## 1. 结论摘要

当前项目不需要推倒重来。渲染兼容、离线优先、歌曲身份、直播领域模型、事件沉淀、播放器和本地备份已经形成了较好的基础。

当前的主要问题不是功能数量不足，而是三条主线还没有完全收口：

1. **产品主线没有压缩成“今晚准备 → 直播 → 复盘 → 下一次学习”的单一任务流。**
2. **浏览器、Electron、API 认证、二进制请求和持久化恢复边界还不够统一。**
3. **UI 功能密度较高，但入口、状态、响应式布局、反馈和类型契约存在漂移。**

因此，下一阶段不建议继续以“增加一套布局、增加一个平台、增加一个技术抽象”作为主要进展标准。更高价值的目标是：

> 让主播打开软件后，能快速知道今晚要做什么；直播中不会丢操作；直播后能直接得到可执行的复盘和学习建议；桌面版可以安全安装、运行、恢复和升级。

### 推荐优先级

| 优先级 | 主题 | 目标 |
|---|---|---|
| P0 | 发布与契约收口 | 生产构建、桌面 API 认证、备份安全、离线行为可信 |
| P0 | 主播核心任务流 | 今日/今晚工作台、海报选歌闭环、直播控制台统一 |
| P1 | 数据与应用架构 | `song_id` 全链路、事务/outbox、manifest 恢复、渲染计划一致性 |
| P1 | UI/UX 重构 | 导航、响应式、播放器、反馈、无障碍 |
| P2 | 平台与扩展 | Electron 发布门、真实指标、Tauri/SQLite/编辑器评估 |

## 3. 当前应保护的产品与技术资产

### 3.1 产品资产

1. **离线优先**：曲库、直播、播放器、海报、统计和备份的核心路径不依赖互联网。
2. **主播场景完整**：歌曲资产、学歌、点歌、弹唱、事件、复盘和内容输出具备闭环基础。
3. **直播领域建模**：请求、队列、演唱结果、权益、规则版本和幂等命令没有被混成一个状态字段。
4. **现场效率设计**：QuickView、键盘快捷键、离线补报和置顶窗口适合直播现场。
5. **本地信任感**：本地数据、加密备份、自动快照和恢复能力是长期留存的重要基础。

### 3.2 技术资产

1. **grid-wrap 金标准保护**：不得因为 Runtime v2 重构而改变历史输出。
2. **模块化单体边界**：当前不需要拆微服务，应用服务、Repository 和渲染核心的边界方向正确。
3. **Repository 可靠性基础**：AtomicJsonWriter、CAS、revision、备份和故障注入值得继续复用。
4. **稳定歌曲身份**：`Song.id` 是未来统计、曲谱、音频、队列和 SQLite 迁移的正确基础。
5. **测试与回归体系**：golden、API、状态机、持久化和 UI 测试应继续保留。

```text
npm run test
```

## 4.2 Electron packaged 模式的 API 传输和认证需要统一

### 证据

- `electron/main.js` packaged 模式使用 `loadFile()`；
- `ui/src/api/client.ts` 默认使用相对 `/api/...` 请求；
- `server/api/handlers.py` 要求 `X-Streamer-Session`；
- `ui/src/electron-bridge.ts` 使用 `X-Session-Token`；
- 多处 UI 仍直接使用 `fetch()`，绕过统一 API client。

### 风险

可能出现“桌面 UI 可以启动，但业务读写、复盘海报或学习报告请求失败”。浏览器开发模式和 Electron packaged 模式也可能表现不一致。

### 建议

建立统一的 Desktop/API Transport：

```text
DesktopTransport
├── API base URL
├── session token
├── X-Request-ID
├── JSON 请求
├── binary 请求
├── timeout / abort
└── 统一错误 envelope
```

建议：

- 统一认证头为 `X-Streamer-Session`；
- 由 preload 安全暴露一次性 token 或桌面 API 配置；
- `apiRequest()` 自动注入 token；
- 增加 `apiBinaryRequest()` 处理 PNG/音频等二进制响应；
- 禁止组件自行实现认证、超时和错误解析；
- 对 packaged 模式增加 smoke test：启动、读数据、改歌、保存海报、导出 PNG、退出。

## 4.3 备份导入必须修复路径安全边界

### 证据

`tools/backup.py:293-302` 目前直接将 zip member name 拼接到 `data_root`：

```python
target = data_root / name
target.write_bytes(zf.read(name))
```

### 风险

恶意备份包可能包含绝对路径、`..` 或 Windows drive path，造成数据目录外写入。

### 建议流程

```text
读取并验证 HMAC/SHA-256
→ 拒绝绝对路径和路径穿越
→ resolve 后确认位于 data_root 内
→ 解压到临时 staging 目录
→ 校验 manifest 和 schema
→ 创建本地快照
→ 原子发布
```

WebDAV pull 也应使用相同 staging 流程，不能直接覆盖正式数据目录。

## 4.4 离线状态不能阻止本地海报导出

### 证据

- `ui/src/App.tsx:360` 将离线导出命令标记为不可用；
- `ui/src/App.tsx:411` 提示“离线状态无法导出海报”；
- `AGENTS.md` 明确要求海报预览、渲染和保存离线可用。

### 建议

将状态拆成：

```text
internet: online/offline
local_backend: ready/unavailable
online_metadata: available/unavailable
webdav: configured/locked/unavailable
```

离线时：

- 本地海报预览、渲染、PNG 导出、原生保存继续可用；
- 在线补全、公开歌单、榜单浏览、WebDAV 同步单独禁用；
- 文案使用“在线增强暂不可用”，不要提示整个导出能力不可用。

## 4.5 QuickView pending 命令必须按 session 隔离

### 证据

`ui/src/quick-view/useLiveSession.ts` 使用全局 localStorage key：

```text
quickview-v2-pending
```

`PendingCommand` 没有 `session_id`，`retryPending()` 会按当前 hook 的 `sessionId` 重放所有命令。

### 风险

直播场次 A 离线产生的命令，在切换到场次 B 后可能被错误补报到 B。

### 建议

- `PendingCommand` 增加 `session_id`；
- retry 只处理当前 session 的命令；
- 网络超时/5xx 可重试；401/403/404/422 不应无限重试；409 应先刷新状态；
- 长期将关键 command journal 移到 Python 本地存储，localStorage 只保留 UI 偏好或短暂缓存。

主播打开应用后 10 秒内回答：

- 有没有未结束的直播？
- 今晚唱什么？
- 哪些歌可以直接唱？
- 下一步是准备、开播还是复盘？

## 5.3 统一 LiveView、QuickView 和 PlayView 的用户心智

产品上应统一称为“直播控制台”，由两个显示面组成：

### 主窗口

- 场次管理；
- 当前歌曲和下一首；
- 队列；
- 待同步命令；
- 待确认演唱结果；
- 规则和权益；
- 直播结束和复盘。

### 速查窗口

- 置顶；
- 快速搜歌；
- 快捷键记录；
- 看谱；
- 进入弹唱；
- 返回控制台。

### 重要业务调整

`PlayView` 的音频 `ended` 不应静默直接等同于“已完整演唱”。建议改为：


## 6. P1：产品与数据架构优化

## 6.1 让 `song_id` 真正贯穿前端

### 当前残留

- `selectedTitles`；
- title 作为 React key、selection key、cursor key；
- `POST /api/songs/status` + `{ title }`；
- `POST /api/songs/delete` + `{ title }`；
- `LearningView` 和 `SongEditDialog` 仍调用 title 兼容接口。

### 建议目标

新 UI 统一使用：

```text
PATCH /api/songs/{song_id}
PATCH /api/songs/{song_id}/status
DELETE /api/songs/{song_id}
POST /api/songs/{song_id}/restore
```

title 路由只保留为 legacy 兼容层，并加入清晰的迁移策略。

### 验收

```text
改名 → 状态切换 → 删除 → 恢复 → 曲谱访问 → 音频访问
```

全程不能依赖旧标题。

---

## 6.2 增加本地事务 / outbox，而不是立即上消息队列

当前部分业务先保存状态再追加事件：

```text
songs.json → events.jsonl
```

进程在两步之间退出时，会造成状态与历史不一致。

建议实现轻量本地事务：

```text
准备状态变更
→ 准备事件
→ 写 operation journal / outbox
→ 原子提交
→ 启动或后台补发事件
```

这套机制未来可直接映射到 SQLite 事务，但当前不需要引入消息队列。

---

## 6.3 将 manifest 视为派生索引

LiveSession 和 Poster 当前存在 state/manifest 分开写入的问题。

建议：

- 实体文件是事实；
- manifest 通过统一 `AtomicJsonWriter` 更新；
- 启动时扫描实体目录，校验并重建 manifest；
- manifest 不决定实体是否存在；
- Live 和 Poster 复用 `ManifestedFileRepository` 能力。

---

## 6.4 收口 RenderDocument / Runtime v2

目标流程：

```text
source snapshot
→ analyze
→ plan
→ render(plan)
```

需要解决：

- `engine_version` 不能固定伪装成 grid-wrap；
- preview、export、batch export 必须使用同一份 plan；
- 当前布局的页数不能固定读取 grid-wrap；
- theme style 数量不能静默截断实际页数；
- magazine-flow 的 analyze、categorize 和 render 必须使用同一画布；
- 未知 layout 异常不能 catch-all 后静默降级为一页；
- layout 应统一使用 `ctx.effective_style`。

### 不变约束

- 不重写 `grid-wrap`；
- 不用新引擎覆盖旧 golden；
- 任何 Runtime v2 收口都必须继续通过金标准。

---

## 6.5 自动同步凭证和远端备份安全

`server/services/auto_sync.py` 当前以 Base64 保存主密码。Base64 不是加密。

建议：

- macOS 使用 Keychain；
- Windows 使用 Credential Manager；
- Linux 使用 Secret Service；
- 系统密钥环不可用时，自动同步默认关闭；
- WebDAV 远端默认上传加密备份，而不是只依赖 HTTPS；
- pull 前显示本地/远端时间、大小和差异摘要；
- 默认先创建本地快照；
- 将“仅下载”和“覆盖本地”拆成两个明确动作。

## 7. P1：UI/UX 重构建议

## 7.1 App Shell 与导航

当前 64px 图标侧栏主要依赖 tooltip，不利于首次使用。

建议：

- 宽屏支持可展开的文字导航；
- 首次启动默认显示文字；
- 按“创作 / 运营 / 成长”分组；
- 设置和帮助放在 secondary navigation；
- 当前视图增加文字标题或 breadcrumb；
- 不让 tooltip 承担完整信息架构。

## 7.2 海报工作台信息架构

统一为：

```text
作品 → 内容 → 样式 → 输出
```

清理：

- 重复主题入口；
- 右侧硬编码布局入口；
- “自由编排规划中”等不是真实能力的正式入口；
- 与当前 layout 页数不一致的分页控制。

## 7.3 响应式与窄屏

当前 800px 以下直接隐藏主要创作能力，属于功能裁剪，不是响应式设计。

建议：

- 左栏改抽屉；
- 参数区改 bottom sheet；
- 预览保留；
- 主题、布局、歌曲来源提供横向选择器；
- 保存和导出固定在底部 action bar；
- `LearningView` 使用单列到双列渐进布局；
- `LiveView` 采用会话列表到详情的单层导航；
- `StatsView` tab 支持横向滚动；
- `PlayView` 顶栏拆成主操作层和设置层。

## 7.4 MiniPlayer

当前 MiniPlayer 只能打开/关闭弹唱，不具备基本播放控制。

建议至少增加：

- 播放/暂停；
- 可操作进度；
- 当前时间和总时长；
- 音频加载失败状态；
- 返回直播上下文。

如果暂时不实现这些能力，应将名称改为“当前播放条”，避免用户产生错误预期。

## 7.5 反馈与错误系统

建议统一规则：

| 场景 | 反馈方式 |
|---|---|
| 首次加载失败 | 行内错误 + 重试，不弹 toast |
| 用户主动操作失败 | toast，可带恢复动作 |
| 批量操作 | 一次聚合 toast，详情内展开逐项错误 |
| 在线增强不可用 | 明确标记在线功能不可用 |
| 本地数据失败 | 显示本地恢复动作和 request id |
| 长错误 | 摘要 + 查看详情，不把整段塞入 toast |

## 7.6 无障碍基础层

统一封装 Dialog、Tabs、Menu、Toast 和 Disclosure，补齐：

- 初始 focus；
- focus trap；
- 关闭后 focus return；
- `aria-labelledby` / `aria-describedby`；
- Tabs 的 `aria-controls`、tabpanel 和键盘方向键；

## 8. 建议的目标架构

```text
┌──────────────────────────────────────────────┐
│ UI Features                                  │
│ Workspace / Library / Live / Player / Stats  │
└──────────────────────┬───────────────────────┘
                       │ typed API client
┌──────────────────────▼───────────────────────┐
│ Platform Adapter                              │
│ Browser / Electron / Future Tauri             │
│ token, save, share, recording, notifications  │
└──────────────────────┬───────────────────────┘
                       │ localhost transport
┌──────────────────────▼───────────────────────┐
│ FastAPI Transport                             │
│ validation / auth / error mapping             │
└──────────────────────┬───────────────────────┘
                       │
┌──────────────────────▼───────────────────────┐
│ Application Services                          │
│ Song / Poster / Export / Live / Backup        │
│ transaction + outbox + job orchestration      │
└───────────────┬───────────────────┬───────────┘
                │                   │
┌───────────────▼──────────┐ ┌──────▼───────────┐
│ Domain + Render Core      │ │ Repository Ports │
│ immutable snapshots       │ │ Song/Event/...   │
│ analyze → plan → render  │ └──────┬───────────┘
└──────────────────────────┘        │
                             ┌──────▼───────────┐
                             │ File / SQLite    │
                             │ assets + index   │
                             └──────────────────┘
```

### 架构原则

1. Python 后端继续是核心数据写入权威；
2. Electron/Tauri 只负责桌面能力，不持有业务真相；
3. UI 只通过统一 API client 访问后端；
4. 渲染器只消费不可变 RenderDocument/Plan；
5. Application Service 统一协调状态、事件和附件；
6. 文件资产与结构化索引分离；
7. SQLite 未来只作为 Repository adapter，不让 UI 直接依赖。

## 10. 明确不建议当前做的事情

### 10.1 不重写 grid-wrap

当前已有 golden 保护。不得用新 Runtime 自举覆盖旧基线，也不得为了统一代码结构删除兼容路径。

### 10.2 不立即迁移 SQLite

178 首左右的曲库不构成迁移理由。应由真实事件量、查询延迟、多窗口并发或全文检索需求触发。

### 10.3 不直接把 Electron 替换为 Tauri

先抽象 DesktopCapabilities，完成 Electron 发布门，再用真实包体积、内存、启动时间、录屏和多窗口数据做 spike 决策。

### 10.4 不提前做完整图片编辑器

遵守 `AGENTS.md` 的启动条件：三套新布局上线并被真实使用后，再评估自由编排编辑器。

### 10.5 不拆微服务

当前是单机离线优先产品。优先解决模块化单体内部的事务、类型和恢复问题，不增加网络部署边界。

### 10.6 不把在线元数据变成必填

歌曲仍必须可以完全离线手工创建、编辑、播放、排版和演出。

### 10.7 不让 localStorage 承担业务真相

localStorage 可以保存 UI 偏好和短暂缓存，不应长期保存直播队列、不可丢失命令或业务事件。

## 12. 最终判断

项目当前最值得保护的组合是：

> 本地优先的数据资产 + 直播现场可靠性 + 曲谱/弹唱能力 + 可解释事件沉淀 + 海报内容输出。

下一阶段的突破不应是继续堆叠能力，而应是把这条路径做成可依赖的日常工作流：

```text
主播打开软件
→ 看到今晚准备状态
→ 一键恢复或开始直播
→ 搜歌、看谱、弹唱、记录不丢
→ 结束后得到复盘和下一步建议
→ 需要时快速产出海报
```

在这个主线完成前，优先级应低于发布收口的工作包括：

- 新增更多布局；
- 立即迁移 Tauri；
- 立即迁移 SQLite；
- 完整图片编辑器；
- AI 海报和智能裁切；
- 继续扩展非核心在线元数据能力。
