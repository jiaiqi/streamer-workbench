## 1. 产品定义与边界

主播工作台不是单一海报生成工具，而是个人音乐主播的本地优先内容与直播运营系统：

1. **歌曲资产**：歌曲身份、歌手、调性、速度、语言、类型、标签、状态和曲谱；
2. **海报创作**：独立维护歌单设计，按需导出，不强制属于某场直播；
3. **直播控制**：点歌、权益核销、插队、队列、当前歌曲、曲谱和演唱结果；
4. **学歌成长**：练习、卡点、乐理、曲谱、学会过程和点歌需求转化；
5. **运营洞察**：请求、演唱、等待、履约、学习和内容产出的可解释统计。

### 1.1 核心原则

- 海报创作与 LiveSession 解耦；直播可以引用海报歌曲集合，引用不是归属；
- 点歌请求与演唱结果分离；未演唱不等于未发生；
- 规则可配置且版本化；历史记录按发生时的规则解释；
- 高价值礼物只产生插队申请资格，不替主播自动做决定；
- 直播现场首先保证少步骤、可恢复、可键盘操作；
- 数据不足时显示“如何积累”，不生成伪趋势；
- 专业功能默认渐进披露，不要求主播先学习音乐软件或数据库概念。

### 1.2 非目标

- 不做直播平台弹幕中台或支付结算系统；
- 不验证平台真实礼物价格，主播配置的等价值仅用于本地运营记录；
- 不做强制账号、云同步或多人协作；
- 不把自定义布局编辑器扩张成通用 Photoshop；
- 不根据点歌人价值自动歧视、屏蔽或永久降低普通请求优先级。

## 3. 信息架构与导航

桌面一级导航保持六项：

| 页面 | 用户心智 | 核心任务 |
|---|---|---|
| 海报 | 独立作品 | 选歌、布局、主题、比例、分类、分页、按需导出 |
| 歌曲 | 长期资产 | 搜索、维护、曲谱、乐理、标签和批量操作 |

| 统计 | 可解释洞察 | 场次、请求人、歌曲、履约、学习和内容产出 |
| 设置 | 全局策略 | 外观、路径、点歌规则、快捷键、安全和诊断 |

移动端完整编辑不是承诺；移动端优先直播控制、歌曲速查和轻量查看。底部导航若无法在 5 项内保持可读，应采用“海报 / 歌曲 / 直播 / 学歌 / 更多”，统计和设置进入“更多”，不缩小到难以触控。

## 4. UI/UX 系统

### 4.1 视觉语言

- **画廊白**：长时间管理和创作；暖白背景、低噪声层级、海洋青主操作色；
- **暗色舞台**：直播和速查；深暖黑、克制舞台金、明确状态；
- 海报 Palette 与应用 UI token 严格分离；
- 金色只表示舞台、权益或需要注意的运营信息，不作为所有 CTA 的装饰；
- 图标使用同一套线性 SVG；不得用 emoji 充当结构图标。

#### 应用主色

界面模式与应用主色是两个正交设置。界面模式决定表面、文字和边框；应用主色只决定导航选中、主按钮、链接、焦点环、进度和选择态。海报 Theme/Palette、成功/警告/危险、会员/礼物状态色均不随应用主色变化。

首发提供 8 个经过亮/暗模式检查的固定方案：竹月青（默认）、雨过天青、远山黛、胭脂红、海棠褐、藤萝紫、琥珀金、松花绿。名称采用中国传统色意象，不宣称色值是唯一历史标准。第一版不开放任意 Hex 输入，避免不可读组合。

设置页使用“色块 + 名称 + 选中边框”展示，点击即时预览；当前项提供 `aria-pressed`，不能只靠颜色表达。正式持久化字段为 `settings.applicationAccentId`，未知值回退 `bambooMoon`。完整裁决见 [`../../ADR-008.md`](../../ADR-008.md)。

### 4.2 密度和层级

- 页面最多一个主要 CTA；
- 高频操作首屏可达，专业参数使用折叠、抽屉或二级对话框；
- 直播页信息密度可以高，但当前歌曲、下一首和处理按钮必须形成唯一视觉焦点；
- 任何状态不能只靠颜色，必须同时有文字或图标；
- 空状态必须说明原因、影响和下一步操作。

### 4.3 操作预算

| 任务 | 目标 |
|---|---|
| 打开直播并恢复队列 | 自动恢复，不增加强制向导 |
| 普通点歌入队 | 歌曲 + 1 次确认；其他字段可空 |
| 有权益点歌 | 歌曲、权益、确认，最多 3 个主要动作 |
| 高价值礼物插队 | 选择权益后才开放位置；必须主播显式确认 |
| 标记已唱 | 单键或一个大按钮 |
| 标记不会唱 | 一个按钮；自动保留请求并生成待学线索 |
| 恢复常用海报 | 打开作品后直接预览；导出是可选动作 |

### 4.4 动效规范

| 场景 | 时长 | 行为 |
|---|---:|---|
| Hover / Press | 120–180ms | 颜色、阴影或轻微缩放，不改变布局尺寸 |
| 队列插入/移位 | 220–360ms | FLIP 或 transform；保持当前歌曲位置稳定 |
| 页签/内容替换 | 180–240ms | crossfade，不闪白 |
| 对话框 | 180–260ms | 遮罩淡入、面板轻上浮 |
| 海报预览刷新 | 220–320ms | 旧图保持至新图完成，再 crossfade |

动画必须可中断，`prefers-reduced-motion` 下取消位移和弹簧，仅保留必要透明度反馈。直播操作不得等待动画结束才落数据。

### 4.5 无障碍和键盘

- WCAG 2.2 AA 为发布门；正文对比度至少 4.5:1；
- 产品内部目标触控区至少 44×44 CSS px，高于 WCAG 2.2 的 24×24 最低要求；
- 焦点环可见且不会被固定底栏遮挡；
- 所有对话框具备标题、关闭、Escape、焦点进入与归还；
- 拖拽排序必须同时提供键盘“上移/下移/移到位置”；
- Space 默认“已唱”，但输入框、下拉框和对话框聚焦时不触发；
- 建议快捷键：`/` 搜索、`Space` 已唱、`U` 不会唱、`P` 延后、`T` 曲谱、`R` 记录点歌；全部可修改并检测冲突。

### 4.6 响应式

- ≥1440：完整三栏或直播双栏 + 洞察区；
- 1100–1439：收窄资源栏，设置区可折叠；
- 800–1099：一栏常驻、一栏抽屉；
- <800：直播控制、速查、轻量海报查看；复杂规则编辑使用全高 Sheet；
- 375px 必须无横向滚动，固定导航不得遮挡最后一项内容。

## 5. 海报工作室

### 5.1 独立作品模型

`PosterDocument` 是可长期保存的独立作品，可选引用歌曲查询、Preset、统计结果或 LiveSession，但不属于 LiveSession。

```ts
type PosterDocument = {
  schemaVersion: number
  id: string
  name: string
  songSource: SongSource
  selectedSongIds: string[]
  grouping: GroupingSpec
  sorting: SortingSpec
  layoutId: string
  themeId: string
  canvasId: string
  pagePolicy: PagePolicy
  parameters: Record<string, unknown>
  exportSettings: ExportSettings
  createdAt: string
  updatedAt: string
  optionalSessionRef?: string
}
```

`optionalSessionRef` 只表示“这份作品曾被某场直播引用”，不能用于删除级联或决定作品生命周期。

### 5.2 布局、主题和比例

- Layout 与 Theme 是多对多关系；主题不得强制归属某布局；
- 每个 Layout 通过能力元数据声明支持的 Theme capability 和 Canvas；
- Theme 通过颜色角色、背景资源和字体角色声明需求；
- 兼容性由能力求交集得到，不维护易漂移的双向手工列表；
- UI 先选布局，再只显示该布局可用比例；主题是独立选择区；
- 切换布局后若当前比例不兼容，必须说明原因并请求选择，不静默替换后直接导出。

```ts
type LayoutCapabilities = {
  supportedCanvasIds: string[]
  requiredThemeCapabilities: string[]
  supportsAutoPagination: boolean
  supportsManualPages: boolean
  supportsGrouping: GroupingKind[]
  maxDensity?: Record<string, number>
}
```

首批画布候选：9:20、9:16、3:4、4:5、1:1、A4。实际可选项以布局算法声明为准，不能为了 UI 完整而谎报支持。

### 5.3 分类和排序

分类是一等配置，不在渲染器中硬编码：

- 不分类；
- 按歌手；
- 按歌名字数区间；
- 按歌曲类型；
- 按语言；
- 按首字母；
- 按掌握状态；
- 按自定义标签；
- 🧪 按调性、速度区间、情绪或演出能量。

每种分类必须定义：空值桶、桶顺序、分类标题、跨页重复标题规则和单桶溢出策略。分类内排序支持手动、歌名、歌手、最近更新和点歌热度。

### 5.4 分页

- 页数由歌曲数量、分类标题占用、布局、比例、字体和内容密度共同计算；
- UI 不允许写死“2 页”；
- `grid-wrap` 的旧兼容输入仍固定两页并受金标准保护；新作品通过显式 `pages=auto` 使用动态分页；
- 自动分页必须在分析阶段返回容量、页数、溢出和降级原因；
- 导出按钮显示实际页数，预览和导出使用同一 `RenderDocument`。

```ts
type PagePolicy =
  | { mode: 'legacy-fixed-2' }
  | { mode: 'auto'; minPages?: number; maxPages?: number }
  | { mode: 'manual'; pages: ManualPage[] }
```

### 5.5 自定义布局

自定义布局在路线图触发条件满足后启动：

- 可新增、删除、复制和重排页面；
- 删除非空页面必须展示内容去向：移至上一页、移至下一页或取消；
- 页面不能只保存像素坐标，元素和锚点使用 0–1 归一化坐标；
- 自动布局和手动页可以混合，但必须明确“自动区”和“固定区”；
- 撤销重做覆盖页面结构、元素、绑定和参数；
- 自定义包导入前执行 JSON Schema 校验、资源大小限制和路径安全检查。

## 6. 直播、点歌和权益

### 6.1 三个不同对象

| 对象 | 含义 |
|---|---|
| `SongRequest` | 观众或主播提出“想听某首歌”的请求 |
| `QueueEntry` | 某次请求在某场直播队列中的当前投影 |
| `PerformanceRecord` | 最终是否演唱、何时演唱及结果 |

同一歌曲可以被多人请求；同一请求最多产生一个最终结果，但可以经历排队、插队、延后等多个变化事件。

### 6.2 默认规则

1. 新加入粉丝团：免费点 1 首；默认有效期为本场，可配置；
2. 主播会员：每天免费点 1 首；默认自然日 00:00 重置，可配置；
3. 墨镜或等价值礼物：兑换 1 首普通排队点歌；礼物名和等值门槛可配置；
4. 更高价值礼物：获得插队申请资格；门槛可配置；
5. 插队必须由主播确认；默认位置可配置为当前歌曲后、第三位或每次手选；
6. 公平保护默认启用：连续插队达到上限后，至少处理一条普通队列。

这些是本地运营规则，不宣称等同于直播平台官方规则。规则修改后生成新 `rule_version`，不回写历史。

### 6.3 权益核销

```ts
type EntitlementGrant = {
  id: string
  ruleVersion: string
  requesterId?: string
  kind: 'fan_join' | 'member_daily' | 'gift_exchange' | 'campaign' | 'manual'
  grantedAt: string
  expiresAt?: string
  quota: number
  consumed: number
  evidence?: { label?: string; value?: number; platformRef?: string }
}
```

- 昵称不是稳定身份；跨场统计需要可选 `requester_id`，没有稳定 ID 时明确标记“按昵称估算”；
- 核销必须幂等，重复提交不能重复扣额度；
- 删除或取消请求是否返还权益由规则配置，默认“未演唱取消则返还，已经开始演唱不返还”；
- 礼物价值只存主播确认值和显示快照，不做财务结算；
- 所有手工覆盖记录操作者、时间和原因。

### 6.4 插队

- 普通点歌、新入团、会员每日权益和基础礼物默认只允许队尾；
- 高价值礼物解锁“申请插队”，不是自动插队；
- 主播确认时保存 `original_position`、`target_position`、`reason`、`confirmed_at`；
- UI 显示“申请”与“已确认”两个不同状态；
- 插队后保持当前正在演唱的歌曲不动；
- 公平保护触发时说明“已达到连续插队上限”，允许主播覆盖但需要原因；
- 调序必须有撤销入口，撤销本身也写事件。

### 6.5 结果状态

```text
requested → queued → current → sung
                 ├→ postponed → queued
                 ├→ unknown → learning_candidate
                 ├→ skipped
                 ├→ cancelled
                 └→ duplicate_merged
```

- `unknown` 表示主播当前不会唱，不能记成取消；
- `postponed` 保持请求有效并移到队尾或指定位置；
- `duplicate_merged` 保留所有点歌人和权益记录，队列只出现一次；
- `skipped` 必须有可选原因，如时间不足、曲谱缺失、状态不佳；
- 每场已唱历史永久可回看，并支持结束后补记或纠错；纠错使用补偿事件，不删除原事件。

### 6.6 直播 UI

- 当前歌曲区：歌名、歌手、调性、Capo、曲谱、点歌人、权益和等待时间；
- 主操作：已唱；次操作：不会唱、稍后再唱、更多结果；
- 队列项：序号、歌曲、点歌人、来源、权益、插队状态、等待时间；
- 本场历史：时间、结果、点歌人、来源、等待和演唱时长；
- 高频点歌人：近 30 天次数、出现场次和履约率，支持“按稳定 ID / 按昵称估算”标记；
- 不会唱线索：累计请求人数、次数、最近请求、礼物次数和一键加入学歌。

### 6.7 离线和故障

- QuickView 本地队列是断网缓存，Python 后端恢复后通过 `event_id` 幂等补报；
- 写入失败时现场操作立即反映为“待同步”，不能冻结队列；
- 同一事件 ID 不同内容视为冲突，进入诊断，不静默覆盖；
- 进程崩溃后恢复队列、当前歌曲、未同步事件和规则版本；
- 直播结束前显示未处理请求、未同步记录和未核销权益摘要。

## 7. 歌曲资产、曲谱与乐理

### 7.1 Song 专业字段候选

| 字段 | 用途 | 阶段 |
|---|---|---|
| `key` / `mode` | 原调与大小调 | 🎯 |
| `preferred_key` | 主播常唱调 | 🎯 |
| `capo` | 吉他变调夹 | ✅/扩展 |
| `tempo_bpm` | 节拍器、串场节奏 | 🎯 |
| `time_signature` | 拍号 | 🧪 |
| `duration_seconds` | 场次时间估算 | 🎯 |
| `vocal_range` | 最高/最低音提示 | 🧪 |
| `energy` | 慢歌/中速/热场 | 🎯 |
| `language` / `genre` / `mood_tags` | 搜索、分类和编排 | 🎯 |
| `chord_progression` | 和弦进行摘要 | 🧪 |
| `difficulty_dimensions` | 音域、节奏、和弦、记词分维度 | 🧪 |

字段必须允许未知；未知不等于 0。专业字段逐步加入 Song 新 schema，并遵循迁移、备份和往返测试。

### 7.2 乐理助手

候选功能按“直播即时价值”排序：

1. **转调助手**：展示原调、主播调、半音差、Capo 建议和实际听感调；
2. **和弦速查**：常用和弦、替代按法、主歌/副歌进行；
3. **串场建议**：按调性距离、BPM、能量和语言寻找自然衔接的下一首；
4. **音域风险**：标记连续高音、最高音和需要降调的位置；
5. **节拍器与倒计时**：练习和开唱前使用，不在直播默认自动播放声音；
6. **结构标记**：Intro / Verse / Chorus / Bridge / Solo，帮助速查定位；
7. **练习卡点**：高音、换气、节奏、和弦切换、歌词等结构化标签。

转调模型必须区分“演奏形状调”和“实际听感调”。ChordPro 的 key/capo/transpose 语义可作为文本曲谱互操作参考；MusicXML 可作为未来结构化谱面交换格式，但 R3 不要求实现完整乐谱编辑器。

### 7.3 曲谱格式策略

- 当前图片/PDF 附件继续支持；
- 🎯 支持 ChordPro 导入/预览，保留 title、artist、key、time、tempo、duration、capo 和 tag；
- 🧪 支持 MusicXML 4.0 只读导入，用于和声、调号、拍号、速度和转调信息；
- 所有导入格式保留原文件和解析版本；解析失败不损坏附件；
- 曲谱版权由用户负责，文件默认仅存本地并排除 Git。

## 8. 统计与建议

### 8.1 直播统计

- 请求次数、去重歌曲数、已唱、不会、跳过、取消；
- 请求到演唱等待时间 P50/P90；
- 按普通、新入团、会员、礼物、高价值礼物拆分；
- 权益授予、核销、返还和过期；
- 插队申请、确认、拒绝、覆盖公平保护次数；
- 点歌人出现场次、请求频率、歌曲偏好和履约率；
- 热门歌曲按“请求量”和“实际演唱量”分别排行；
- 不会唱需求榜按独立请求人数优先，而不是单个用户重复次数。

### 8.2 学习统计

- 练习天数、分钟、自评和卡点分布；
- 从不会唱请求到加入学习、学会、首次演唱的转化漏斗；
- 歌曲学习周期；
- 高频请求但尚未学会的机会列表；
- 调性、音域、节奏或和弦难点的个人分布。

### 8.3 建议系统约束

- 所有建议必须展示理由，例如“近 30 天 6 人点过且你已练习 3 次”；
- 少于阈值时不输出百分比趋势；
- 建议只是推荐，不自动修改状态、队列或规则；
- 可关闭某类建议；不使用点歌人身份推断敏感属性。

## 9. 领域与服务架构

```text
Presentation
├── Poster Studio / Library / Live / Learning / Stats / Settings
├── QuickView
└── Electron shell

Application
├── PosterService / RenderService / ExportService
├── LiveSessionService / RequestService / QueueService
├── EntitlementService / RequestPolicyService
├── LearningService / MusicKnowledgeService
└── StatsService

Domain (core/)
├── Song / Tab / MusicMetadata
├── PosterDocument / LayoutCapabilities / RenderDocument
├── LiveSession / SongRequest / QueueEntry / PerformanceRecord
├── RequestPolicy / EntitlementGrant / PolicyDecision
└── Event

Infrastructure
├── JSON repositories / JSONL EventStore / file assets
├── FastAPI schemas + routers
├── Pillow layout/render adapters
└── Electron lifecycle + constrained bridge
```

Router 不复制规则；`RequestPolicyService` 负责资格判断，`QueueService` 负责调序，`EntitlementService` 负责幂等核销，应用服务在一次命令中协调状态写入和事件追加。

### 9.1 一致性边界

JSON 多文件无法提供数据库事务时，命令采用：

1. 验证请求与规则版本；
2. 生成稳定 command/event ID；
3. 在锁内写当前投影；
4. 追加事实事件；
5. 若事件追加失败，记录 recovery journal 并阻止同命令再次核销；
6. 启动时重放 recovery journal；
7. 达到迁移门后切 SQLite 单事务。

涉及权益核销和队列调序后，SQLite 迁移门应从“仅一万行”升级为组合条件：出现跨文件原子性故障、统计查询持续超预算、需要并发写或多设备同步时评估迁移。

## 10. API 目标

| 端点 | 方法 | 用途 |
|---|---|---|
| `/api/posters` | GET/POST | 作品列表和创建 |
| `/api/posters/{id}` | GET/PATCH/DELETE | 作品保存和删除 |
| `/api/layouts/{id}/capabilities` | GET | 比例、主题能力、分页和分类支持 |
| `/api/posters/{id}/preview` | POST | 冻结 RenderDocument 后预览 |

| `/api/live-sessions/{id}/queue` | GET | 当前队列投影 |
| `/api/live-sessions/{id}/queue/reorder` | POST | 普通调序或主播确认插队 |
| `/api/live-sessions/{id}/requests/{rid}/result` | POST | 已唱、不会、延后、跳过、取消 |

| `/api/music/transpose` | POST | 目标调、Capo 和和弦转调建议 |

所有请求/响应使用 Pydantic；OpenAPI 生成 TypeScript 类型；错误结构统一为 `code/message/details/recovery/trace_id`。写命令接受 `command_id` 以支持离线重试幂等。

## 11. 事件目标

建议的新事件类型：

```text
request_created
request_matched / request_unmatched
entitlement_granted / entitlement_consumed / entitlement_refunded / entitlement_expired
queue_added / queue_reordered / queue_postponed / queue_removed
priority_requested / priority_confirmed / priority_rejected / fairness_overridden

request_merged
policy_published

```

事件保留 `event_id`、`type`、`source`、发生时间和 schema 版本，并扩展 `session_id/request_id/requester_id/rule_version/command_id`。设计借鉴 CloudEvents 的唯一 ID、来源、类型、时间和 schema 标识思想，但不要求 events.jsonl 完整实现 CloudEvents 网络封装。

## 12. 安全、隐私和数据保留

- 点歌人昵称和平台 ID 属个人运营数据，默认只存本地；
- UI 提供按点歌人删除/匿名化历史的能力，聚合统计可保留不可逆计数；
- 不保存支付凭证；礼物只记录名称、主播确认价值和可选平台引用；
- 导出或诊断包默认排除点歌人身份，除非用户明确勾选；
- Electron 启用 `contextIsolation`、sandbox、CSP、导航限制和最小 `contextBridge`；
- 导入主题、曲谱和布局时校验扩展名、MIME、大小、路径穿越和 Schema；
- 日志不得写会话令牌、完整文件内容或不必要的点歌人标识。

## 15. 验收场景

### 场景 A：会员每日点歌

系统识别或主播选择“会员每日权益” → 显示今日剩余额度 → 加入队尾 → 幂等核销 → 演唱后写历史 → 次日按规则重置。重复提交不能扣两次。

### 场景 B：高价值礼物插队

选择高价值礼物 → 只显示“可申请插队” → 主播选择位置并确认 → 系统记录原位置、目标位置和规则版本 → 当前歌曲不被打断 → 队列平滑重排 → 可撤销。

### 场景 C：点了不会的歌

请求保留点歌人和来源 → 主播点击不会唱 → 请求结果记为 unknown → 自动生成待学线索 → 统计累计独立请求人数 → 学会后关联首次演唱，不改写原历史。

### 场景 D：独立海报

主播打开长期保存的常用歌单 → 选择 grid-wrap、任意兼容主题和比例 → 按歌手分类 → 自动计算 3 页 → 按需导出；全流程无需创建直播场次。

### 场景 E：个性化应用主色

主播在设置中选择“雨过天青” → 导航、主按钮、焦点和进度即时平滑更新 → 切到暗色舞台仍保持可读 → 重启后恢复选择 → 原有海报预览和再次导出逐像素不变。

- [SQLite 使用场景](https://www.sqlite.org/whentouse.html)：当查询、事务或数据规模越过已定义门槛时的迁移依据。

这些规范约束实现质量，不取代本项目的产品规则、ADR 和金标准。
