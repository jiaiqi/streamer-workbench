## 2. localStorage

新键名：`quick-view-storage-v2`。

```json
{
  "version": 2,
  "queue": [],
  "pending_events": [],
  "unresolved_queue": [],
  "unresolved_pending_events": []
}
```

兼容读取的旧键：

- `tonight-queue-v1`：`[{"title":"知足","sung":false,"addedAt":123}]`
- `quick-events-pending-v1`：`[{"type":"song_sung","title":"知足","ts":"2026-07-29T00:00:00"}]`

迁移仅在歌曲列表加载成功后执行，以 title 在当前曲库中唯一匹配。重复旧队列项按
`song_id` 稳定去重，保留最早加入时间和已唱真值。无法解析的队列和事件分别进入
`unresolved_queue`、`unresolved_pending_events`，在界面可见且不会自动上报。

如果 v2、旧 queue 或旧 pending JSON 损坏，迁移返回错误，不写 v2，不覆盖原键。
成功写入 v2 后重复加载直接验证并复用 v2，结果幂等。旧键暂不删除，作为迁移期恢复来源。

## 3. pending 重试语义

事件产生时先把完整 Event v2 信封写入 v2，再发起网络请求：

```json
{
  "event_id": "evt_<uuid_without_dashes>",
  "type": "queue_added",
  "song_id": "song_...",
  "title_snapshot": "知足",
  "occurred_at": "2026-07-29T00:00:00.000Z",
  "source": "quick-view"
}
```

- 浏览器优先使用 `crypto.randomUUID()`，降级使用 `crypto.getRandomValues()`；
- 保序发送，首个失败立即停止；
- 只有 2xx 响应才按 `event_id` 删除已完成项；
- 网络错误和非 2xx 均保留原事件、原 `event_id`、原 `occurred_at`；
- 非 2xx 响应正文显示在 QuickView 诊断区域，不静默吞掉冲突；
- 新事件加入期间的旧请求完成，只删除明确成功的 ID，不会误删乱序加入的事件。

## 5. 剩余风险

- localStorage 仍只是离线缓存；完整 LiveSession 与跨设备同步属于 R1/R2；
- 冲突事件目前由用户可见诊断提示并保留，尚无逐条放弃/导出诊断的交互；
- R0.8 统一 API client 前，QuickView 仍直接调用 `fetch`。
