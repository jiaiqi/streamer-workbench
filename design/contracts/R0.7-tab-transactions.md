# R0.7 曲谱附件跨资源事务契约

> 状态：已实现
> 最后更新：2026-07-29
> 适用范围：`/api/songs/{identity}/tabs` 上传、列表、删除与启动恢复

## 1. 目标与边界

一次曲谱写操作同时影响三类状态：

1. `data/tabs/{song_id}/` 中的附件文件；
2. `songs.json` 中 `Song.tab_files`；
3. `events.jsonl` 中来源为 `tabs-api` 的 `song_edited` 事件。

Router 只负责读取 multipart/query 输入、调用 `TabApplicationService` 和映射错误。身份解析、路径验证、Repository revision/CAS、文件发布、事件生成与恢复全部属于应用服务。

本阶段不引入 SQLite 或分布式事务。采用同一 `data_root` 内的原子文件移动、原子 journal 和 Repository CAS，保证重启后可以判定为完整提交或完整回滚。

## 2. 不变量

- 物理目录和 `tab_files` 只使用不可变 `song_id`；title 仅为兼容查询入口；
- 对外可见文件存在时，最终必须能在 `Song.tab_files` 中找到相同路径；
- `Song.tab_files` 引用存在时，最终必须存在对应文件；
- Repository CAS 失败不得留下对外可见的新文件，也不得丢失原删除文件；
- 同一 Python 进程内，相同 `data_root` 的多个服务实例必须共享写锁，同名上传不得互相覆盖；
- 删除不是不可逆 `unlink`，内容保留在 `data/backups/tab-transactions/<transaction_id>/content`；
- 事件使用 journal 中预先生成的固定 `event_id`，恢复补报必须幂等；
- journal 损坏、身份不一致或未知阶段不得猜测修复，必须阻止 AppContext 发布。

## 3. 事务目录

```text
data/backups/tab-transactions/
└── tabtx_<uuid>/
    ├── journal.json
    ├── content                 # 上传暂存或删除后的可恢复内容
    └── rolled-back-content     # 回滚上传保留的输入
```

`journal.json` 使用原子 JSON writer 发布，至少保存：事务 ID、操作、阶段、song_id、title_snapshot、relative_path、固定 Event v2 和时间戳。事务 ID 只由服务端生成。

## 4. 上传状态机

```text
prepared
  → file_published
  → metadata_published
  → committed

prepared/file_published
  → rolled_back（CAS 或发布失败）
```

顺序：

1. 校验 song_id、扩展名、10 MB 上限和安全文件名；
2. 将完整内容刷盘到事务目录，原子发布 `prepared` journal；
3. 原子移动到 `tabs/{song_id}/`，记录 `file_published`；
4. 以加载时 revision 保存新增 `tab_files` 的歌曲库；
5. 记录 `metadata_published`，追加固定事件；
6. 记录 `committed`。

Repository 保存失败时，新文件移入 `rolled-back-content`，歌曲元数据保持旧值。若进程在文件移动后、阶段记录前退出，恢复器以事务目录中是否仍有 `content` 判定文件是否已经发布，避免误移动并发产生的同名文件。

## 5. 删除状态机

```text
prepared
  → file_staged
  → metadata_published
  → committed

prepared/file_staged
  → rolled_back（CAS 或发布失败）
```

删除先把原文件原子移动到事务目录，再用 CAS 删除 `tab_files` 引用。CAS 失败时文件移动回原路径；提交成功后内容继续留在事务目录，允许后续显式恢复或按保留策略清理。

## 6. 启动恢复

应用 lifespan 在发布 AppContext 前调用 `tab_service.recover()`：

- 上传事务且元数据包含路径：确认文件存在，幂等补报事件并提交；
- 上传事务且元数据不含路径：撤回已发布文件并回滚；
- 删除事务且元数据不含路径：幂等补报事件并提交；
- 删除事务且元数据仍含路径：恢复暂存文件并回滚；
- `committed`/`rolled_back`：不重复处理；
- 无法解析的目录：加入 `unresolved`，抛 `RepositoryRecoveryRequired`，应用不进入 ready。

恢复器不静默删除未知文件，不根据 title 猜测身份，不覆盖已存在的恢复目标。
恢复判定使用 `operation × phase × metadata × staged × target` 显式状态矩阵；只接受状态日志最多落后一个已刷盘原子副作用的可达组合，双存、双缺和阶段矛盾一律 unresolved。

## 7. HTTP 与错误语义

- 未找到歌曲或曲谱：404；
- 文件类型、大小、路径或身份无效：400；
- 上传只读取 `10MB + 1 byte`，并校验扩展名与声明 MIME 的对应关系；
- 业务错误统一返回带 `request_id` 的 JSON error envelope；
- Repository 冲突：统一 Repository 409；
- 元数据已提交但事件待恢复：503，提示重启后自动恢复；
- 未知/损坏事务：启动失败，不暴露半可用工作台。

## 8. 自动化证据

- 正常上传/删除：文件、元数据、两条事件一致；
- 上传 CAS 冲突：新文件不可见、元数据不变、无成功事件；
- 删除 CAS 冲突：原文件与元数据均恢复；
- 上传在 `file_published` 后崩溃：重启回滚；
- 上传在 `metadata_published` 后崩溃：重启提交并幂等补报；
- 删除在 `metadata_published` 后崩溃：重启提交并保留可恢复内容；
- 元数据与物理文件矛盾、未知 journal 阶段：不得猜测提交，必须报告 unresolved；
- 同一数据根双服务实例并发同名上传：串行提交为两个独立文件，元数据与事件均不丢失；
- journal 事件身份串改、发布失败、删除暂存后崩溃、事件持久化后响应丢失均有故障证据；
- 上传/删除的目标与暂存文件双存，以及删除引用存在但两者双缺，均阻止猜测恢复；
- 真实 FastAPI lifespan 重启：自动恢复发生在 AppContext 发布前。
