# R0.5 实施契约：Song 关系全链路迁移

> 状态：冻结，允许按变更流程修订  
> 负责人：角色 A（契约、服务端主链路、集成）  
> 协作者：角色 B（Tabs、Preset、QuickView 关系消费者）  
> 创建日期：2026-07-28  
> 上位依据：ADR-004、ADR-005、活跃路线图 R0.5 / R0.11、数据路线图 S3.5

## 1. 目标

完成 `Song.id` 在曲谱、现场队列、Preset 和新事件中的稳定关联。歌曲改名后，所有关系继续指向同一首歌；旧 title 关系可重复迁移、可诊断、可回退。

## 2. 非目标

- 不在本工作包实现完整 AppContext、Repository 或 Pydantic API 单源；
- 不迁移用户数据目录；
- 不开发 LiveSession 完整模型；
- 不删除现有 title 兼容 API；
- 不修改 `grid-wrap` 或任何金标准输出；
- 不直接迁移仓库 `data/`，先完成 dry-run 和组合测试。

## 3. 身份不变量

1. `Song.id` 是不可变、无业务含义的唯一身份，格式为 `song_<uuid hex>`；
2. `Song.title` 是可修改的显示字段，不得作为新长期关系的唯一键；
3. `title_snapshot` 只用于历史显示、离线降级和审计，不能替代 `song_id`；
4. 新建或更新的 tabs、queue、Preset 和 Event v2 关系必须包含有效 `song_id`；
5. 歌曲删除后，历史事件和现场快照可保留 `song_id + title_snapshot`，不得级联删除历史；
6. 迁移无法解析的旧关系不得静默丢失，必须进入报告或孤儿清单。

## 4. 目标 Schema

### 4.1 QuickView 队列

```ts
interface QueueItem {
  song_id: string;
  title_snapshot: string;
  sung: boolean;
  added_at: number;
}
```

恢复队列时优先以 `song_id` 关联当前曲库并显示最新 title；歌曲不存在时显示 `title_snapshot` 并标记为缺失关系。

### 4.2 QuickView 待补事件

```ts
interface PendingEvent {
  event_id: string;
  type: "queue_added" | "song_sung";
  song_id: string;
  title_snapshot: string;
  occurred_at: string;
  source: "quick-view";
}
```

重试必须复用原 `event_id`。localStorage 是断网缓存，不是业务身份真相。

QuickView v2 存储信封除 `queue` 与 `pending_events` 外，允许增加类型明确的
`unresolved_queue` 与 `unresolved_pending_events`。两者只保存旧 title 关系的可见诊断，
不参与正常队列身份判断，也绝不自动上报。损坏的 v2 或旧版 JSON 不得被覆盖，
QuickView 必须保留原始 localStorage 并显示可恢复错误。

### 4.3 Preset

```json
{
  "song_query": {
    "custom_ids": ["song_..."]
  }
}
```

`custom_ids` 只允许 `song_id`。旧数据若保存歌名，由迁移器使用当前曲库精确匹配；未匹配和多义匹配进入迁移报告。

### 4.4 Tabs

目标物理目录：

```text
data/tabs/{song_id}/{filename}
```

`Song.tab_files` 继续保存相对 `data/` 的路径：

```text
tabs/{song_id}/{filename}
```

迁移过程中旧 `tabs/{title}/` 不立即删除。文件复制/移动、歌曲 JSON 更新和验证全部成功后，才能把旧目录移入可恢复迁移备份。

## 5. API 契约

### 5.1 Song ID 主接口

```text
GET    /api/songs/{song_id}
PATCH  /api/songs/{song_id}
DELETE /api/songs/{song_id}
PATCH  /api/songs/{song_id}/status
```

- 路径中的 `song_id` 按不可变 ID 精确匹配；
- `PATCH /api/songs/{song_id}` 的 body 是可编辑字段集合；`id` 不可编辑；
- 改名撞车返回 409；
- 资源不存在返回 404；
- 成功响应返回包含 `id` 的当前歌曲快照；
- 删除响应保留被删歌曲的 `id` 和 `title_snapshot`。

### 5.2 title 兼容接口

以下接口在 R0.5 保留，不新增消费者：

```text
POST /api/songs/update
POST /api/songs/delete
POST /api/songs/status
```

它们继续接受 title，并在内部解析为 Song 后执行与 ID 主接口相同的操作。前端迁移完成前不得删除；后续弃用由 R0.8 类型化 API 统一处理。

### 5.3 Tabs 路径兼容

R0.5 暂时保留 `/api/songs/{identity}/tabs` 路径形状。处理器必须：

1. 先将 `{identity}` 作为 `song_id` 精确查找；
2. 未找到时按 title 精确查找并标记为兼容调用；
3. 新写入只使用解析后的 `song.id` 作为物理目录；
4. 响应同时返回 `song_id`、当前 `title` 和 `tab_files`。

### 5.4 Event v2 写入

- 新 QuickView 上报必须提交 `event_id`、`song_id`、`title_snapshot` 和 `occurred_at`；
- R0.5 期间允许旧客户端用 title 上报，但服务端必须解析到当前 Song.id 后才能写入；
- 显式提交不存在的 `song_id` 返回 404，不得退回 title 指向另一首歌；
- 无 `song_id` 且 title 无法解析返回 400；
- 服务端以当前歌曲 title 刷新 `title_snapshot`；
- 重复 `event_id` 的等价补报幂等，不等价补报拒绝。

## 7. 迁移算法

迁移器必须支持 `--dry-run`，默认不得改变源数据：

1. 读取并校验 songs v4/v5，构造规范化 title → song_id 映射；
2. 扫描旧 tab 目录、Preset 和显式提供的 queue 快照；
3. 输出 planned / unchanged / unresolved / conflict；
4. 发现重复 title、目标文件冲突或非法 ID 时停止；
5. 写入前备份 songs、presets、tabs 和待迁移快照；
6. 先生成目标数据到临时位置；
7. 验证数量、文件哈希和关系引用；
8. 原子替换 JSON；
9. 旧目录移入迁移备份，不直接删除；
10. 再次运行应得到 unchanged，不产生第二份关系。

## 8. 组合测试矩阵

必须覆盖：

1. 添加歌曲并获得稳定 ID；
2. 为该 ID 添加曲谱；
3. 将 ID 加入 queue 和 Preset；
4. 按 ID 修改 title；
5. 按原 ID 仍可获取歌曲；
6. 曲谱路径、queue、Preset 和 Event 仍引用原 ID；
7. title 兼容 API 在迁移期继续工作；
8. 改名撞车不改变任何关系；
9. 删除歌曲后历史事件保留 ID 和 snapshot；
10. v4 songs、title tab 目录、旧 Preset 和旧 queue 可迁移；
11. 未解析关系进入报告；
12. dry-run 无写入；
13. 重复迁移无副作用；
14. 迁移失败可恢复原数据。
