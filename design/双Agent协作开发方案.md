# 主播工作台：双 Agent 协作开发方案

> 状态：活跃协作规范  
> 创建日期：2026-07-28  
> 适用范围：R0–R7 的双 Agent 协作开发  
> 路线图真相：[`产品优化方案终版-0727/路线图.md`](产品优化方案终版-0727/路线图.md)  
> 数据规格真相：[`roadmap-data-stats.md`](roadmap-data-stats.md)

本文定义两个可替换的协作角色，不绑定具体模型、厂商或 Agent 名称。每次开始新工作包时，可将任意合适的 Agent 指派为角色 A 或角色 B；角色可以在工作包之间交换，但同一工作包进行中不得无交接地交换。

本文只规定协作方式、责任边界和建议批次，不替代主规格、路线图、数据路线图或 ADR。发生冲突时，以项目既有真相层级为准。

---

## 1. 协作目标

采用“双 Agent、单路线图、契约先行、边界并行、集中集成”的模式：

1. 两个角色共享同一阶段目标和退出条件；
2. 通过文件所有权和接口契约减少同时修改；
3. 高耦合的架构、领域身份和跨层契约由角色 A 收口；
4. 边界清楚、可独立验收的能力包由角色 B 实现；
5. 角色 A 负责最终集成，角色 B 负责第二视角审查；
6. 阶段完成以自动化证据和真实使用证据为准，不以文件、类或提交数量为准。

当前唯一活跃阶段仍是 R0。R0 完成前，不扩充主题数量、不启动完整编辑器，也不绕过身份与应用边界问题直接推进后续产品功能。

## 2. 两个可替换角色

### 2.1 角色 A：架构、契约、集成与验收负责人

角色 A 是当前工作包的技术主责和集成人，负责高耦合、高回归风险内容：

- 拆解路线图阶段和工作包；
- 起草并冻结跨模块实施契约；
- 维护领域身份、应用边界和 API 单源契约；
- 决定兼容、迁移、回滚和弃用策略；
- 维护金标准和关键组合测试；
- review、集成角色 B 的提交；
- 运行完整质量门并判断退出条件；
- 同步 README、路线图、ADR 和活跃规格状态。

角色 A 可以实现代码，但不应独占所有开发。其首要责任是消除歧义、稳定接口并确保两个工作流最终可合并。

### 2.2 角色 B：独立能力包、测试补强与第二审查负责人

角色 B 承接边界清晰、可独立交付的能力包：

- 按已冻结契约实现独立模块；
- 补齐单元、迁移、异常和兼容测试；
- 搜索遗漏的 title 关联、全局状态、裸 fetch、非原子写等技术债；
- 提供变更摘要、测试证据和剩余风险；
- 对角色 A 的集成结果做第二视角审查；
- 发现契约缺口时先提出变更请求，不私自改变公共接口。

角色 B 不是单纯执行者。其独立审查职责用于发现角色 A 可能遗漏的边界条件，但最终集成裁决仍由角色 A 承担。

### 2.3 角色替换与交换

- 角色与具体 Agent 解耦；Codex、Kimi 或其他 Agent 均可担任任一角色。
- 角色可以在两个工作包之间交换，以匹配上下文、工具能力或工作负载。
- 工作包进行中如需更换 Agent，原 Agent 必须先提交交接记录。
- 新 Agent 应先读取 `AGENTS.md`、活跃路线图、相关 ADR、实施契约和交接记录，再修改代码。
- 更换角色不改变验收标准、分支或文件所有权。

交接记录至少包含：

```text
工作包与当前状态
已完成提交
未提交修改
公共契约与关键假设
已运行测试
失败或未覆盖测试
已知风险
下一步精确入口
允许修改和禁止修改的文件
```

## 3. 真相层级与不可违反边界

发生分歧时按以下顺序裁决：

1. `AGENTS.md` 铁律；
2. `design/产品优化方案终版-0727/产品优化方案终版.md`；
3. `design/产品优化方案终版-0727/路线图.md`；
4. `design/roadmap-data-stats.md`；
5. ADR-001～ADR-005；
6. 当前工作包实施契约；
7. 当前代码实现。

任何角色均不得：

- 修改、删除或移动 `.archive/`；
- 根据 `design/archive/` 决定当前状态或执行顺序；
- 用新引擎自举覆盖 `tests/golden/`；
- 给 `Song` 新增 `pinned`；
- 改变 `grid-wrap` 固定两页兼容行为；
- 将 UI token 混入 Palette v1；
- 在 `core/` 引入 FastAPI、Electron、React 或 PySide6；
- 未经迁移、备份和回滚验证直接修改真实用户数据；
- 在三套新布局真实上线前启动完整图片编辑器。

## 4. 分支、worktree 与提交规范

### 4.1 分支

每个 feature 或 bug fix 使用独立分支，不在 `master` 直接开发。建议按工作包命名：

```text
feature/r0-song-relations
feature/r0-app-context
feature/r0-repositories
feature/r0-api-contract
fix/r0-local-security
chore/r0-toolchain
```

角色 A 可维护一个阶段集成分支，例如：

```text
feature/r0-foundation-integration
```

合并顺序：角色分支 → 阶段集成分支 → 完整验收 → `master`。

### 4.2 worktree

两个 Agent 并行操作时必须使用独立 worktree，避免共享工作区切分支、暂存区或未提交修改：

```text
streamer-workbench-role-a/
streamer-workbench-role-b/
playlist-poster-generator/       # 集成或主工作区
```

不得通过 reset、checkout 覆盖或清理另一个角色的修改。

### 4.3 提交

- 原子提交；
- 中文摘要；
- Conventional Commits 风格；
- 不 force push；
- 提交消息示例：

```text
feat(data): 将曲谱关系迁移至 song_id
refactor(server): 引入 AppContext 与应用工厂
fix(security): 收紧本地服务来源与会话鉴权
test(data): 补充歌曲改名组合回归
```

---

## 5. 工作包实施契约

所有跨角色工作必须先由角色 A 起草实施契约，角色 B 审阅后再并行开发。契约至少包含：

```text
目标与非目标
输入、输出和数据 Schema
公共接口与错误语义
兼容、迁移和回滚策略
允许修改的文件
禁止修改的文件
双方依赖和合并顺序
测试矩阵
完成定义
```

契约冻结后，任何公共接口变更都必须先更新契约并通知另一角色。不得让一侧代码默默改变另一侧依赖。

---

## 6. 文件所有权

文件所有权按工作包冻结，不是永久归属。默认划分如下：

| 区域 | 默认角色 |
|---|---|
| 领域身份、`core/data/songs.py` | A |
| AppContext、AppPaths、应用工厂 | A |
| 应用服务接口、API 模型、类型生成 | A |
| 核心组合测试与金标准验收 | A |
| Tabs 实现与迁移 | B |
| Preset 存储与完整 CRUD | B |
| QuickView queue 与离线补报 | B |
| Repository 文件系统适配器 | B |
| Electron 安全与生命周期 | B |
| 跨平台工具链与遗漏审计 | B |
| 路线图状态和最终集成 | A |

若一个文件必须由双方修改，应拆分提交并约定先后顺序；不能安全拆分时，该文件只指定一个编辑者，另一角色通过 review 提建议。

## 7. R0 详细计划

### Batch 1：R0.5 `song_id` 全链路与 S3.5 收口

#### 角色 A

- 冻结 Song v5 关系契约；
- 规定 ID 主路由与 title 兼容路由；
- 明确 `title_snapshot` 仅用于显示和历史审计；
- 设计 tabs、queue、Preset 的迁移顺序；
- 设计真实数据的 dry-run、备份、验证和回滚；
- 调整歌曲和事件服务端主链路；
- 建立改名组合测试。

#### 角色 B

- 将曲谱存储迁移为 `data/tabs/{song_id}/`；
- 保留旧 title 目录的可重复迁移和失败恢复；
- 将 QuickView queue 改为 `song_id + title_snapshot`；
- 将待补事件改为稳定 `event_id + song_id + occurred_at`；
- 迁移旧 localStorage 队列；
- 明确 Preset `custom_ids` 为 `song_id[]`；
- 迁移旧 Preset 歌名集合，无法匹配项不得静默丢失；
- 完成 Preset CRUD 和迁移测试。

#### 联合验收

按以下顺序完成组合测试：添加曲谱 → 加入队列 → 加入 Preset → 歌曲改名 → 验证曲谱、队列、Preset、统计关系全部保留。旧数据迁移必须可重复、可回退。

Batch 1 通过后，S3.5 才能标记完成。

### Batch 2：R0.6 AppContext 与 R0.7 Repository

#### 角色 A：AppContext

- 新增 `AppConfig`、不可变 `AppPaths` 和 `AppContext`；
- 实现 `create_app(config)`；
- 使用 lifespan 管理初始化和关闭；
- 移除 `server/deps.py` 的模块级可变路径；
- Router 只从当前请求获得上下文；
- 后台任务显式接收依赖和冻结输入；
- 建立多 app、不同临时目录的隔离测试；
- 保持现有 uvicorn 启动方式兼容。

#### 角色 B：Repository

- 实现 Song、Settings、Preset Repository 和 EventStore 适配器；
- JSON 统一使用临时文件、flush 和原子 replace；
- 每个 Repository 管理自己的进程内锁；
- 保留 songs 滚动备份；
- 避免 Preset 内容和 manifest 半写；
- 增加 EventStore ID 去重索引或等价机制；
- 实现损坏文件恢复测试；
- 导出使用冻结的 `RenderDocument`；
- 增加并发写与崩溃恢复测试。

#### 联合验收

两个 app 数据完全隔离；并发写不损坏文件；写入异常保留最后有效版本；重复事件不重复入库；导出期间的数据修改不污染已冻结输入。

### Batch 3：R0.8 API 契约与前端状态

#### 角色 A：后端契约

- 使用 Pydantic 请求/响应模型替代裸 `dict`；
- 统一错误结构与状态码；
- 生成 OpenAPI 和 TypeScript 类型；
- 建立关键 API 合约测试；
- 标记兼容接口的弃用策略。

#### 角色 B：前端契约消费者

- 用生成类型替换重复手写类型；
- 建立统一 `apiClient`；
- 清理散落的裸 `fetch`；
- 统一加载、空、错误和重试状态；
- 导出轮询支持失败、超时、取消和重试；
- Settings、Library、Learning、QuickView 全部接入统一约定。

#### 联合验收

OpenAPI 可重复生成前端类型且无意外 diff；前后端 Song 类型包含稳定 `id`；主要页面覆盖加载、空、错误和重试；后端断开时现场队列不丢失。

### Batch 4：R0.9 用户目录与 R0.10 本地安全

#### 角色 A：用户目录契约

- 实现平台默认路径算法；
- 明确开发、测试和正式模式；
- 明确启动参数、环境变量和配置文件优先级；
- 实现目录验证、切换、失败回滚和首次迁移；
- 保证无 UI 时也可配置目录；
- 同步 ADR-003 和 README。

#### 角色 B：本地服务与 Electron 安全

- 后端只绑定 loopback；
- 移除任意来源 CORS；
- 设置开发和桌面来源白名单；
- 使用每次启动的随机会话令牌；
- Electron 请求携带令牌；
- 增加 CSP、导航限制、新窗口限制和外链策略；
- 安全配置 BrowserWindow；
- 处理启动超时、异常退出和孤儿进程；
- 防止日志泄露令牌。

### Batch 5：R0.11、R0.12 与总验收

#### 角色 B

- 收齐 Preset/API 欠账；
- 修复 Makefile 对 `python` 别名的依赖；
- 提供统一测试 runner；
- 自动处理 Windows UTF-8；
- 统一临时目录和环境复现说明；
- 增加活跃文档链接检查；
- 清理旧品牌名称残留。

#### 角色 A

- 审核 R0 全部退出条件；
- 运行完整测试矩阵；
- 更新 README、路线图、数据路线图和必要 ADR；
- 只在证据齐全后将 R0 标记完成；
- 给出进入 R1 的集成基线和已知风险。

## 9. 交付、review 与集成流程

每个工作包使用以下循环：

1. 角色 A 发布实施契约和文件所有权；
2. 角色 B 复述边界、依赖和验收条件；
3. 双方在独立 worktree/分支开发；
4. 每个原子能力独立提交；
5. 角色 B 提交工作包交付报告；
6. 角色 A review 并集成；
7. 角色 A 运行完整回归；
8. 角色 B 对集成结果做第二视角审查；
9. 问题修复或退回原工作包；
10. 证据齐全后更新阶段状态。

交付报告必须包含：

```text
修改摘要
提交列表
文件列表
数据和接口变更
兼容、迁移和回滚说明
已运行测试及结果
未运行或未覆盖测试
已知风险
是否影响真实 data
是否影响金标准
建议合并顺序
```

日常状态不按“写了多少代码”汇报，而按以下格式：

```text
已证明
未证明
新发现风险
阻塞项
下一可合并节点
```

## 12. 核心管理结论

双 Agent 协作的目标不是让两个 Agent 始终同时修改代码，而是让两个可替换角色围绕同一契约，在不重叠的文件和责任边界内并行，并在每个可验证节点汇合。

当前最佳起点是 R0.5：角色 A 负责身份、服务端契约和集成；角色 B 负责 Tabs、Preset、QuickView 等关系消费者。完成全链路改名组合测试后，再并行推进 AppContext 与 Repository。
